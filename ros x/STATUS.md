## 2. 구현된 것

### 2.1 파일 구성

```
test/
├── STATUS.md    이 파일 — 설계·구현·검증·계획 전부
├── tof.py       모든 판단 + MQTT publish + 웹 화면 + 리소스 모니터
└── mqtt.py      MQTT → ROS2 /cmd_vel 변환 (판단 없음)
```

**파일 2개가 전부다.** 시각화는 `image.py`(matplotlib/터미널) → `web.py`(별도 웹서버)
→ **tof.py 내장** 순으로 옮겨왔다 — 이유는 §2.6.

**개발 원칙 준수**: 라파2에 ROS 패키지 미생성, 순수 Python, 라파1 구조 무변경,
MQTT는 Python 코드 간 통신 전용, ROS2 publish는 mqtt.py 단독.

### 2.2 tof.py — 제어 연산

모든 판단을 이 프로세스 하나에 모았다. 안전 규칙이 여러 파일에 흩어지면
낭떠러지 차단이 우회될 수 있기 때문이다.

| 구성요소 | 역할 |
|---|---|
| `SerialReader` ×3 | ToF 시리얼 → 8x8 그리드(mm). 끊기면 3초 후 자동 재연결 |
| `JoystickReader` | evdev로 컨트롤러 직접 읽기. 축 자동 감지, 핫플러그 대응 |
| `CliffDetector` ×3 | 하단 2행(R6·R7) 절대 800mm 기준 낭떠러지 판정 |
| `Controller` | 기존 `assist_controller_node.py` 로직 이식 |
| main loop 20Hz | 융합 → 명령 생성 → MQTT publish |

**판단 우선순위** (위에서부터, 먼저 걸리면 확정):

```
1. 낭떠러지        → 전진 차단, 회전·후진 허용     [최우선]
2. 조이스틱 무입력  → 완전 정지
3. 장애물 없음     → 조이스틱 그대로
4. 전진 의도 없음   → 조이스틱 그대로
5. 좌·우 모두 막힘  → 정면 뚫림이면 직진, 막혔으면 정지
6. 측면 벽 근접    → 벽 반대로 회전, 전진 0
7. 전방 장애물     → 더 열린 쪽으로 비례 조향
```

**낭떠러지 규칙이 한 줄로 성립하는 이유**:

```python
out.linear_x  = min(manual_lin, 0.0)   # 전진(양수)→0 차단, 후진(음수)→통과
out.angular_z = manual_ang             # 회전 자유
```

요구사항 4개(전진 차단 / 강제 정지 / 정상까지 유지 / 좌우·후진 허용)가
`min(x, 0)` 하나로 전부 만족된다.

### 2.3 8x8 그리드 행 분할

기존 프로젝트가 "바닥을 읽는다"며 **버리던 하단 행을 낭떠러지 감지에 사용**한다.
두 용도가 정확히 상보적이라 같은 프레임에서 동시에 판단할 수 있다.

```
 R0~R1  미사용 (천장·먼 배경)
 R2~R4  장애물 감지 ROI  → 최소거리 = 그 방향 대표 거리
 R5     미사용 (바닥·배경 경계 — 장면에 따라 원경이 섞여 불안정)
 R6~R7  낭떠러지 감지 ROI → 바닥 거리, 800mm 초과 시 낭떠러지
```

### 2.4 낭떠러지 감지 방식

**하단 2행(R6·R7)의 중앙값이 800mm를 넘으면 낭떠러지**로 판정한다.

```
신호 (a) 거리 급증  : median(R6~R7 유효값) > 800mm      ← 절대 기준
신호 (b) 무효 급증  : 유효셀 비율 < 40%   (빔이 바닥을 못 만남)

디바운스: 진입 3프레임(0.15s) / 해제 10프레임(0.5s)  ← 안전 방향 비대칭
```

**왜 R5를 뺐나** (2026-08-06 변경). R5는 바닥과 배경의 경계 행이라 장면에 따라
원경이 섞여 들어와 중앙값을 흔든다. R6·R7은 항상 바닥만 본다.

| 행 | front | left | right |
|---|---|---|---|
| R5 | 395 | 504 | 498 ← 경계, 장면 따라 튐 |
| R6 | **302** | **402** | **368** |
| R7 | **243** | **296** | **276** |

**왜 절대 기준인가** (2026-08-06 변경). 원래는 평지 바닥을 EMA로 학습한 적응형
기준선 대비 +120mm로 판정했다. 장착 각도·높이를 모르는 상태에서는 그게 맞았지만,
지금은 실측이 끝났다 — 바닥이 270~336mm이고 **30초/119샘플 변동폭이 10~11mm**다.
800mm는 바닥의 **2.4~3.0배**라 오탐 여지가 사실상 없고, 판정 지점이 장면·기준선과
무관하게 항상 같아 예측 가능하다.

기준선 학습은 그대로 유지한다 — 판정에는 안 쓰지만 **바닥 형상 검증**(§5 11번)과
화면 표시에 필요하다. 상대 판정은 `cliff_delta_mm`으로 되살릴 수 있으나 기본은
`None`이다. 둘을 같이 켜면 상대 쪽이 약 420mm에서 먼저 걸려 절대 기준이
무의미해지기 때문이다.

> **절대 기준은 워밍업 중에도 적용된다.** 낭떠러지 위에서 tof.py를 켜도 잡히고,
> 그 값을 평지로 학습하지도 않는다. 적응형 단독일 때 있던 구멍이다.

> 바닥이 임계값의 70%(560mm)를 넘으면 **여유 부족 경고**를 띄운다. 센서를 더 높이
> 달거나 각도가 얕아지면 오탐 위험이 생기는데, 그 전에 알려준다.

### 2.4b 장착 형상 역산 (2026-08-06)

R6·R7 실측 슬랜트 거리와 행당 각도(FoV 45°÷8행 = 5.625°)로 장착 높이·각도를
역산했다. `d = h / sin(θ)` 두 식을 연립하면 미지수 2개가 풀린다.

| 센서 | R6/R7 실측 | 장착높이 | 내림각 R6/R7 | 지면 도달 (센서 기준) |
|---|---|---|---|---|
| front | 302/243mm | 111mm | 21.6°/27.2° | **216~281mm 앞** |
| left | 402/296mm | 105mm | 15.1°/20.7° | 277~388mm 앞 |
| right | 368/276mm | 102mm | 16.2°/21.8° | 256~353mm 앞 |

**낭떠러지 반응 여유** — R7이 지면에 닿는 216mm 지점에서 모서리를 만나고,
`cliff_on_frames` 3프레임(150ms) 뒤 확정된다:

| 속도 | 디바운스 중 전진 | 확정 시 모서리까지 |
|---|---|---|
| 0.05 m/s | 7.5mm | 209mm |
| 0.10 m/s | 15mm | 201mm |
| 0.22 m/s (최대) | 33mm | **183mm** |

최대 속도에서도 **18cm 이상** 남는다. 다만 이건 *센서 기준* 거리다 —
센서가 앞바퀴 접지점보다 뒤에 있으면 그만큼 빼야 한다. **실측 필요.**

### 2.4c ⚠ 장애물 ROI가 바닥을 본다 — 여유 119mm

같은 형상으로 장애물 ROI(R2~R4)를 검사하니 문제가 나왔다.

| 센서 | R4 내림각 | R4가 바닥에 닿는 거리 | `front_enter`(500mm) 대비 |
|---|---|---|---|
| **front** | 10.3° | **619mm** | **여유 119mm** |
| left | 3.9° | 1556mm | 여유 1056mm |
| right | 4.9° | 1196mm | 여유 696mm |

front의 R4는 바닥을 619mm에서 만난다. 즉 **빈 복도에서도 front 거리가 619mm를
넘지 않는다** (min을 쓰므로 바닥이 상한이 된다). 실제 장애물이 더 가까우면
정상적으로 잡히므로 감지 자체는 문제없지만, **여유가 119mm뿐이다.**

> **front 센서를 2.5°만 더 숙이면 R4의 바닥 거리가 500mm 아래로 내려가
> 상시 '장애물 있음'이 되어 전진이 영구 차단된다.** 한 행(5.6°)의 절반도 안 되는
> 여유다. 낭떠러지 감지를 위해 각도를 조정한 결과 이쪽 여유가 얇아졌다.

원래 `obstacle_roi_rows = [2,4]`는 기존 프로젝트의 장착 각도 기준값이다.
이 장착에서 R4는 0.5m 앞의 높이 2cm 지점을 스치는 '바닥 긁는 행'이라,
낮은 장애물(문턱·바닥의 물건)을 잡아주는 대신 여유를 깎아먹는다.

**판단 보류** — `[2,3]`으로 줄이면 여유가 851mm로 넉넉해지지만 낮은 장애물을
놓친다. 실주행에서 어느 쪽이 나은지 보고 정한다 (§6 5단계).

### 2.5 mqtt.py — 순수 변환기

받은 값을 그대로 `TwistStamped`로 옮긴다. 판단하지 않는다.
유일한 예외가 **워치독**인데, 이는 판단이 아니라 통신 장애 시 안전 정지다.

- 0.5초 무수신 → zero 발행 (로봇이 마지막 명령으로 계속 달리는 것 방지)
- `seq` 기반 유실·순서역전 감지, 오래된 명령 폐기
- NaN/inf 명령 거부
- SIGTERM/SIGINT 시 정지 명령 발행 후 종료

> ⚠ **`Twist`가 아니라 `TwistStamped`**. Jazzy `turtlebot3_node`는 `TwistStamped`를
> 구독한다. plain `Twist`는 **에러 없이 조용히 실패**해 모터가 안 움직인다.

### 2.6 웹 화면 (tof.py 내장)

```bash
python3 tof.py                 # 브라우저: http://192.168.0.40:8080
```

**왜 tof.py 안에 넣었나.** 시리얼 포트는 한 프로세스만 열 수 있다. tof.py가 3개를
점유하므로 별도 프로세스는 8×8 원본을 MQTT로 우회해 받아야 했고, 그러면 아무도 안 보는
그리드 토픽을 10Hz로 계속 발행해야 한다. 같은 프로세스면 그 우회가 통째로 사라진다.
파일도 2개로 줄었다.

**대신 제어 루프와 스레드로 분리했다.** 제어 루프가 하는 일은 최신 프레임 *참조*를
락 안에서 대입하는 것뿐이고, JSON 직렬화(64셀×3)와 네트워크 쓰기는 전부 웹 스레드 몫이다.
브라우저가 몇 개 붙든 느리든 끊기든 루프는 기다리지 않는다. **포트를 못 열어도
경고만 남기고 제어는 그대로 진행한다** — 시각화 때문에 로봇이 멈추면 안 되니까.

> 실측: 브라우저 2개를 붙인 채로도 **제어 루프 20.0Hz 유지**. CPU는 +14%p 올랐지만
> 그 부담은 전부 웹 스레드가 졌다. (§2.8)

| 경로 | 용도 |
|---|---|
| `/` | 대시보드 (외부 CDN·라이브러리 0개 — 오프라인에서 그대로 동작) |
| `/stream` | SSE — 프레임 오는 즉시 push, 유휴 시 1초 하트비트 |
| `/state` | 현재 상태 JSON 1회 (디버깅·스크립트용) |
| `/sys` | CPU·메모리만 따로 (터미널 `watch` 용) |
| `/healthz` | 살아있는지 확인 |

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--no-web` | — | 웹 화면 끄기 |
| `--web-host` | `0.0.0.0` | 외부 접속 허용. 로컬만 열려면 `127.0.0.1` |
| `--web-port` | `8080` | |
| `--no-sysmon` | — | 리소스 모니터 끄기 |
| `--grid` | 꺼짐 | 8×8 원본을 MQTT로도 발행 (원격 구독용, 웹에는 불필요) |

**GStreamer/MJPEG 대신 SSE + 숫자 전송**을 쓴다. 영상 스트리밍은 서버가 픽셀로
구워서 보내는 방식이라 8×8 숫자 192개에는 과하고(인코딩 CPU + 지연), 브라우저에서
셀 값을 읽거나 확대할 수 없다. 숫자를 그대로 흘리면 전송량이 적고 지연이 낮으며
**셀마다 mm 값이 그대로 보인다.** SSE는 단방향이라 WebSocket의 양방향성이 필요 없고,
끊기면 브라우저(`EventSource`)가 알아서 재접속한다.

화면에 나오는 것: mode 배지 / 수신 상태 / 낭떠러지 배너 / 좌·정면·우 8×8 격자(mm 값) /
행 라벨 색(장애물 ROI 파랑 / 낭떠러지 ROI 보라 — 실제 설정값을 따라 표시) / **조이스틱 입력(파랑) vs 최종 출력(초록) 바** /
리소스 카드. 파랑과 초록의 차이가 회피 로직이 개입한 양이다.

**갱신이 끊기면 화면을 흐리게+탈색**한다. 마지막 프레임이 남아 실시간 값처럼 보이는
것이 가장 위험한 오해라서 배지 텍스트뿐 아니라 형태로도 알린다.

**셀 색 = 로봇의 판정 구간** (2026-08-06 변경). 단일 색조 램프에서 5구간 다색으로
바꿨다. 경계값을 색이 예뻐 보이게 나눈 게 아니라 **제어 파라미터에서 그대로 끌어온다** —
색 경계가 곧 로봇의 판정 경계다.

| 색 | 구간 | 뜻 |
|---|---|---|
| 🟥 빨강 `#d33c42` | ~200mm | **정지** (`front_stop_distance`) |
| 🟧 주황 `#e88434` | 200~500mm | **회피 진입** (`front_enter_threshold`) |
| 🟨 노랑 `#deb433` | 500~800mm | **주의** (`cliff_abs_mm`) |
| 🟦 하늘 `#a8ddf2` | 800~1500mm | 여유 |
| 🟩 연초록 `#dff7df` | 1500mm~ | 안전 |

임계값을 바꾸면 색 경계도 따라 움직인다 (`WebView.bands()`가 CONFIG에서 계산).

**검증** (dataviz 검증기, 어두운 패널 `#171a21` 기준):

- **명도가 거리에 따라 단조 증가** — 흑백으로 봐도, 색각 이상이어도 순서가 읽힌다.
  인접 구간 ΔL ≥ 0.06, 표면 대비 전 구간 ≥ 3.7:1 (순서형 검사 전 항목 통과)
- **가장 중요한 경계인 빨강↔주황(정지 vs 회피)이 가장 크게 벌어져 있다** —
  CVD ΔE 13.3 / 정상시야 16.2로 두 기준 모두 통과
- 약한 쌍은 주황↔노랑(ΔE 7.5)과 하늘↔연초록(10.8)인데, **둘 다 같은 의미 계층
  안**(주의끼리, 안전끼리)이라 혼동해도 판단이 달라지지 않는다

무지개 램프를 magnitude에 쓰지 말라는 원칙에서 의도적으로 벗어난 부분이다.
이 화면은 연속적인 크기가 아니라 **이산적인 상태**(정지/회피/주의/여유/안전)를
보여주는 status 인코딩이고, 위험이 즉시 눈에 띄어야 하기 때문이다. 대신 그 원칙이
막으려던 문제(순서를 못 읽음)는 명도 단조 증가로 해결했다.

**색 단독으로 뜻을 전하지 않는다** — 셀마다 mm 숫자가 찍히고, 범례에 구간별
거리와 이름이 함께 나온다. 무효 셀은 구간 밖 중립 회색('값 없음'은 '먼 거리'가
아니다). 낭떠러지는 **빨간 테두리 + 텍스트 배너**로 이중 표시한다.

### 2.7 리소스 모니터 (tof.py 내장)

1초마다 `/proc`를 읽는 별도 스레드. `psutil` 없이 파일 몇 개만 읽으므로 비용이 사실상 0.

| 카드 | 내용 |
|---|---|
| tof.py | CPU%, RSS, 스레드 수, 제어 Hz |
| mqtt.py | CPU%, RSS, 스레드 수 — **없으면 "실행 안 됨" 빨간 카드** |
| 시스템 CPU | 전체 CPU%, load average |
| 메모리 | 사용/전체 MB |
| CPU 온도 | 80°C 넘으면 스로틀링 경고 |

**CPU%는 `top`과 같은 기준** — 코어 1개 = 100%. 라파5는 4코어라 상한이 400%고,
50%는 '4코어 중 반 코어'다. 카드 미터는 전체 코어 대비(÷4)로 채운다.

> **`mqtt.py` 카드가 "실행 안 됨"이면 안전 신호다.** mqtt.py가 죽으면 라파1에 명령이
> 전혀 안 간다. 그런데 tof.py는 멀쩡히 돌고 웹 화면도 정상으로 보인다 — 이 카드가
> 없으면 알아챌 방법이 없다.

터미널에서 따로 보고 싶으면:

```bash
watch -n1 'curl -s http://localhost:8080/sys | python3 -m json.tool'
```

### 2.8 실측 성능 (2026-08-06, 라파5 4코어 / 8GB)

| 항목 | 실측 |
|---|---|
| MQTT `robot/cmd` (tof.py → mqtt.py) | **19.96 Hz** — 간격 평균 50.1ms, 최대 52.0ms, **유실 0/199** |
| ROS2 `/cmd_vel` (mqtt.py → 라파1) | **20.000 Hz** — min 0.050s, max 0.051s, std dev 0.19ms |
| 메시지 크기 | 373 B → **7.3 KB/s** |
| tof.py | CPU 42~50% (**4코어 중 11~13%**), RSS 28MB, 8스레드 |
| mqtt.py | CPU **2%**, RSS 68MB, 16스레드 |
| 브라우저 2개 접속 시 tof.py | CPU 64% (+14%p) — **제어 20.0Hz 유지** |
| CPU 온도 | 50~51°C (스로틀링 80°C 한참 아래) |

**질문 답**: MQTT도 ROS2도 **둘 다 20Hz**다. tof.py의 메인 루프가 20Hz로 돌면서
매 사이클 MQTT를 발행하고, mqtt.py는 받는 즉시 `/cmd_vel`로 변환해 내보낸다.
mqtt.py는 자체 주기를 갖지 않고 들어온 만큼 그대로 흘린다 — 그래서 지터가
0.19ms로 극히 작다. MQTT 구간 지연이 그대로 ROS 구간에 반영되는 구조다.

tof.py CPU의 대부분은 **ToF 3채널 시리얼 파싱**이다(프레임마다 8행 정규식 매칭 ×3).
제어 연산 자체는 미미하다. mqtt.py의 RSS 68MB는 대부분 `rclpy`/DDS 런타임이고,
CPU 2%는 그냥 메시지를 옮기기만 하기 때문이다.

**여유는 충분하다.** 둘을 합쳐 4코어 중 약 13%, 메모리 96MB / 7.9GB.

### 4.4 조이스틱 실주행 (35초, 699프레임)

```
조이스틱 입력   : 572건 (81%)
조이스틱 linear : -0.20 ~ +0.20   ← scale_linear 전 범위
조이스틱 angular: -1.00 ~ +1.00   ← scale_angular 전 범위
출력     linear : -0.15 ~ +0.02
출력     angular: -1.00 ~ +1.00
mode 분포: NORMAL 313, AVOID_RIGHT 259, STOP 127
```

이 숫자들이 로직 동작의 증거다:

- **STOP 127건** — 스틱에서 손을 떼면 정지 (데드맨)
- **AVOID_RIGHT 259건** — 센서 0.21~0.24m 상황에서 `right(0.23) > left(0.21)` →
  더 열린 우측 선택. 판단 정확
- **출력 linear 최대 +0.02** — 장애물이 `front_stop(0.20)` 직전이라 비례 감속이
  전진을 거의 0까지 줄임
- **출력 linear 최소 -0.15** — 조이스틱 -0.20을 `v_min` 클램프가 -0.15로 자름

컨트롤러 축: `ABS_Y`(전진/후진), `ABS_X`(좌/우회전), 중립 128, 드리프트 +0.004
(데드존 0.05로 충분히 흡수).

### 10·11번 상세 — 오른쪽 센서 정렬과 기준선 오학습

**증상**: 웹 화면에서 정면·왼쪽은 R5~R7이 바닥인데 오른쪽만 값이 밀려 보였다.
세 센서의 행별 중앙값을 실측해 원인을 특정했다.

| 행 | front | left | right (조정 전) | right (조정 후) |
|---|---|---|---|---|
| R5 | 391 | 526 | 1217 | **498** |
| R6 | 302 | 392 | 1158 | **377** |
| R7 | 241 | 294 | 668 | **285** |

조정 전 오른쪽은 R0~R6이 전부 1.1~1.5m 원경이고 바닥은 R7 한 줄뿐이었다.
**약 2~3행(11~17°) 위를 보고 있었다** (VL53L8CX FoV 45° ÷ 8행 ≈ 5.6°/행).

`cliff_roi_rows = [5,7]` 이 낭떠러지를 판정하는데 그 행들이 바닥이 아닌 배경을
보고 있으면, 기준선이 배경 거리로 학습되어 **회전할 때마다 오탐이 나고 진짜
낭떠러지는 미탐**이 된다. 소프트웨어로 행을 밀어도 쓸 수 있는 바닥 행이 R7
하나뿐이라 근본 해결이 안 되므로 **물리 조정이 정답**이었다.

**조정 후 오른쪽이 왼쪽과 거의 일치**(498/377/285 vs 504/401/301)해 해결됐다.

**그 과정에서 11번이 드러났다.** 조정 중(로봇을 들거나 기울인 상태)에 tof.py 를
켜자 기준선이 `left 2402mm / front 1212mm / right 645mm` 로 학습됐다 — 전부 바닥이
아닌 배경이다. front 는 가짜 낭떠러지까지 래치됐다. 그런데도 **에러가 하나도 안 났다.**

그래서 워밍업이 끝나는 순간 낭떠러지 ROI 행중앙값이 **바닥 형상인지 검사**한다:

```
바닥을 비스듬히 보면 아래 행일수록 가까워진다 → 단조 감소 + 총 낙차 30mm 이상
벽·배경을 보면 행마다 비슷하거나 들쭉날쭉하다
```

절대 거리로는 장착 높이·각도를 알 수 없어 판정이 불가능하므로 **모양**으로 본다.
어긋나면 콘솔에 경고 + 행중앙값을 찍고, 웹 화면 기준선 표기가 빨간
`⚠ 바닥 아님` 으로 바뀐다. 8건 단위 검증 통과(실측 정상 3케이스 + 배경·역전·
무효행·평평 4케이스 + 조정 전 right).

2번이 가장 중요했다. 안전 관련 코드는 **정상 경로보다 종료·실패 경로에서 더 자주 깨진다.**

> 3·4·5번은 터미널/matplotlib 렌더링 문제였고, 시각화를 브라우저로 옮기면서
> 원인 자체가 사라졌다. 폰트·정렬을 브라우저가 처리하므로 `fonts-nanum` 도 더는 필요 없다
> (설치돼 있어도 무해). 기록으로만 남긴다.

### 14번 상세 — 측면 센서가 ±45°가 아니다

전동 휠체어 프로젝트를 참고해 tof_2.py 에 3D 기하를 넣으면서, 장착각을 실측으로
확인하다 발견했다. **CLAUDE.md/README 의 "좌·우 45°"는 설계 의도이고 실물이 아니다.**

**측정 방법** — 평평한 벽을 정면으로 마주보면 세 센서가 보는 모든 점의 z(전방거리)가
같아야 한다. 좌우 센서는 비스듬히 보므로 사선 거리는 열마다 다르지만, 장착각이 맞으면
3D 변환 후 z 가 한 값으로 모인다. **z 의 흩어짐이 최소가 되는 각도**가 정답이다.

| 센서 | 설정(문서) | 역산 | z 흩어짐 |
|---|---|---|---|
| front | +0.0° | **−0.2°** | 18.8mm |
| left | −45.0° | **−10.2°** | 91.3 → 21.4mm |
| right | +45.0° | **+14.0°** | 84.7 → 18.7mm |

front 가 −0.2° 로 나온 것이 **장면 유효성 검증**이다 — front 의 좌우 장착각은
정의상 0° 이므로, 0 이 안 나오면 각도 문제가 아니라 벽을 제대로 안 보고 있다는 뜻이다.
(첫 시도에서 front 가 −20.8° 로 나와 결과를 폐기했다. 이 게이트가 없었으면
멀쩡한 설정을 망칠 뻔했다.)

**독립 교차검증** — 최소거리 비. 벽을 마주보면 벽에 가장 수직인 광선이 최소값을 준다:

| 센서 | 최소거리 | front 대비 | ±45°라면 |
|---|---|---|---|
| front | 580mm | 1.000 | — |
| left | 572mm | **0.988** | 1.082 |
| right | 559mm | **0.965** | 1.082 |

두 방법이 독립적으로 일치했고, 사용자가 육안으로도 확인했다.

**영향 — 이게 진짜 문제다**

| | 설계 ±45° | 실물 ±12° |
|---|---|---|
| 전체 수평 시야 | −67.5°~+67.5° (**135°**) | −32.7°~+36.5° (**69°**) |
| 센서 간 중복 | 0% | **49%** |
| 옆 벽(200mm) 보이는 시점 | 83mm 앞부터 | **270mm 앞부터** |

**센서 3개 중 사실상 1.5개어치만 쓰고 있다.** 그리고 `left`/`right` 를 "측면 공간"으로
해석하는 로직이 전부 근거를 잃는다 — 둘 다 거의 정면을 본다. 실측에서
left 0.222 / right 0.221 로 거의 같게 나오는 것이 그 증거다.

이에 직접 영향받는 tof.py 규칙:
- 규칙 6 (측면 벽 근접 → 반대로 회전) — 로봇 바로 옆은 세 센서 모두 못 본다
- 규칙 7 (더 열린 쪽으로 조향) — 좌우 시야가 24° 차이뿐이라 분별력이 약하다
- 규칙 5 (좌우 모두 막힘) — front 와 거의 같은 정보로 판정한다

**조치**: tof_2.py 에 실측값(−10.2 / +14.0)을 반영했다. 다만 이건 잘못된 기하를
소프트웨어로 정확히 기술한 것이지, **좁아진 시야 자체를 되돌리지는 못한다.**
근본 해결은 센서를 ±45° 로 재장착하는 것이다 (§6 참조).

**재측정**: `python3 tof_2.py --calib-wall` (평평한 벽 정면 0.4~1.0m, 8초)

### 13번 상세 — 회전이 명령의 56%였던 이유 (OpenCR 펌웨어)

**4단계(바퀴 띄우고 모터 검증)에서 발견.** 부호는 전부 정상이었는데 회전 크기가 안 맞았다.

**측정** — `joint_states.velocity` 를 믿지 않고 **엔코더 위치(rad)를 적분**해 실측했다:

| 명령 | 좌우 바퀴 선속도 차 | 축간거리 역산 |
|---|---|---|
| 전진 0.10 m/s | — (양쪽 +0.0991) | ✅ 정확 (바퀴 반지름은 두 모델 동일) |
| 회전 0.5 rad/s | 0.0799 m/s | **0.160m = burger** |
| 회전 1.0 rad/s | 0.1592 m/s | **0.160m = burger** |

`ros2 param get /turtlebot3_node wheels.separation` 은 `0.287`(waffle)을 반환하는데
실제 동작은 0.160 이었다. **어디서 변환되는지**를 가리는 결정적 실험을 했다 —
파라미터를 0.574(2배)로 바꿔도 바퀴 속도가 그대로였다(0.0795→0.0785→0.0801, 오차 범위).

> **운동학 변환은 라파이가 아니라 OpenCR 펌웨어 안에서 일어난다.**
> `turtlebot3_node` 의 `wheels.separation` 은 **오도메트리 계산에만** 쓰인다.
> 그래서 ROS 쪽을 waffle 로 맞춰도 펌웨어가 burger 면 소용이 없다.

실제 축간거리를 자로 재서 **287mm(Waffle) 확인** → 펌웨어가 틀린 것으로 확정.
소프트웨어로는 물리적 축간거리를 알 방법이 없어 이 확인이 필요했다.

**조치**: `~/opencr_update/update.sh /dev/ttyACM0 waffle.opencr`
(`fw_name: waffle`, CRC DA48FE 일치, flash_write 1.51s)

**재검증**:

| 명령 | 재플래시 전 | 재플래시 후 |
|---|---|---|
| 회전 0.5 rad/s | 0.278 rad/s (56%) | **0.498 rad/s** ✅ |
| 회전 1.0 rad/s | 0.555 rad/s (56%) | **1.000 rad/s** ✅ |
| 전진 0.10 m/s | 0.0991 ✅ | 0.0994 ✅ |

> **교훈**: TurtleBot3 는 모델별 펌웨어를 OpenCR 에 굽는다. `TURTLEBOT3_MODEL`
> 환경변수와 `.yaml` 파라미터를 맞춰도 **펌웨어가 다르면 실제 거동이 다르다.**
> 라파1 `.bashrc` 가 `burger` 로 되어 있던 것과 무관하지 않아 보인다.

### 12번 상세 — 조종이 계속 끊기던 이유

**증상**: 컨트롤러로 조종하면 중간중간 멈추고, 스틱을 다시 움직여야 재개된다.

**원인**: `joy_timeout`(0.3s)을 **마지막 축 이벤트 시각** 기준으로 쟀다. 그런데
evdev는 **값이 바뀔 때만** 이벤트를 낸다 — 스틱을 한 방향으로 고정하면 아무
이벤트도 안 온다. 실측으로 확인했다: **12초 동안 이벤트 0개.**

그래서 0.3초 뒤 `read()`가 `(0, 0, False)`를 반환 → `mode=STOP` → 정지.
스틱을 흔들면 이벤트가 생겨 잠깐 움직이다 또 멈춘다. 타임아웃이 '컨트롤러가
끊긴 것'을 막으려던 건데 **'가만히 잡고 있는 것'까지 끊긴 걸로 오판**했다.

**수정**: `read_loop()` 대신 `select`로 돌면서, 이벤트가 없는 동안에도 **장치가
살아있으면**(`/dev/input/eventN` 존재) 0.15초마다 하트비트로 타임스탬프를 갱신한다.
`joy_timeout`(0.5s)은 이제 '입력이 없다'가 아니라 **'리더 스레드가 죽었거나 장치가
사라졌다'**를 뜻한다 — 원래 의도한 것.

**검증** (가상 게임패드로 '한 번만 입력하고 침묵' 재현):

| 시나리오 | 결과 |
|---|---|
| 스틱 고정 12초 | `engaged=True` **40/40 샘플**, 전진 0.118 유지, `mode=NORMAL` |
| 장치 제거 | ~1.2초 내 `mode=STOP`, 출력 0, 실제 컨트롤러 재탐색 |

부수적으로, **연결 시점에 스틱이 이미 꺾여 있으면** 경고를 띄운다. 그 상태에서는
evdev가 이벤트를 안 주므로 로봇이 안 움직이는데, 값을 그대로 가져다 쓰면 실행하자마자
로봇이 튀어나가므로(재연결 시엔 더 위험) 그렇게 하지 않고 이유를 알려준다.

**8·9번은 둘 다 "고장을 정상으로 보이게 하는" 부류**라 우선 고쳤다. 값이 틀린 것보다
**틀렸다는 걸 숨기는 것**이 위험하다. 9번은 `bash -c '... python3 mqtt.py'` 래퍼의
cmdline 에도 `mqtt.py` 가 들어있어서 생겼다 — 실행 파일이 python 인지까지 확인해야 한다.

### 6번 상세 — 무효값 해석 결함

`treat_stale_as_blocked` 는 "센서 미연결"을 대비한 안전장치인데, **"센서는 멀쩡히
프레임을 보내는데 그 방향에 아무것도 없는 경우"** 까지 막힘으로 처리하고 있었다.

| 상황 | 올바른 판정 | 수정 전 |
|---|---|---|
| 프레임 자체가 안 옴 (0.5초+) | 센서 고장 → **막힘** | 막힘 ✅ |
| 프레임은 오는데 ROI 셀 전부 무효 | 사거리 내 물체 없음 → **열림** | 막힘 ❌ |

실제로 우측 센서가 빈 공간을 향하고 있을 때 `right = 0.0m`(막힘)으로 잡혀
**로봇이 우측으로는 절대 회피하지 않는 상태**였다. 센서가 프레임을 보내고
있다는 것 자체가 살아있다는 증거이므로, 그 상태의 "아무것도 안 잡힘"은 빈 공간이다.

이제 `sensor` 필드로 세 상태를 구분한다: `ok` / `empty` / `offline`.
보수적으로 가려면 `empty_roi_as_open: False` 로 되돌릴 수 있으나, 그러면 빈 공간을
향한 센서가 영구히 막힘으로 잡힌다. (검은색·흡수성 표면이 `empty` 로 보일 위험은
남는데, 이는 ToF 센서의 원리적 한계다.)

### 2단계 — ROI 행이 맞는지 확인

```bash
python3 tof.py            # 브라우저에서 http://192.168.0.40:8080 열기
```

8×8 격자에서 행 용도를 확인한다 (행 라벨 색이 ROI를 표시한다):

| 행 | 라벨 색 | 정상이면 |
|---|---|---|
| R2~R4 | 파랑 (장애물) | **앞쪽 공간**의 거리. 손을 앞에 대면 값이 떨어짐 |
| R6~R7 | 보라 (낭떠러지) | **바닥**. 값이 안정적이고 아래로 갈수록 **짧아짐** |

**틀렸을 때** — 예컨대 R2~R4가 이미 바닥을 보고 있으면 센서가 너무 아래를
향한 것이다. 물리적 각도를 조정하거나 `tof.py` 상단 `CONFIG` 에서:

```python
'obstacle_roi_rows': [2, 4],   # 위로 올리려면 [1, 3]
'cliff_roi_rows':    [6, 7],   # 그에 맞춰 조정
```

두 ROI는 **겹치지 않게** 유지할 것. 낭떠러지 ROI 행은 아래로 갈수록 값이
**짧아져야** 한다 — 그렇지 않으면 기동 시 `⚠ 바닥 아님` 경고가 뜬다.

### 3단계 — 낭떠러지 실측 튜닝

로봇을 **책상 끝으로 천천히 밀면서** 화면을 본다.
**반드시 붙잡을 수 있는 상태로 진행.**

**통과 기준**: 앞바퀴가 모서리에 닿기 **전에** `cliff[C..]` 로 바뀌고
`mode: CLIFF_BLOCK` 이 될 것.

| 증상 | 조정 |
|---|---|
| 너무 늦게 감지 | `cliff_abs_mm` ↓ (800 → 600) |
| 평지에서 오탐 | `cliff_abs_mm` ↑ (800 → 1000). 단 기동 시 여유 부족 경고부터 확인 |
| 깜빡거림 | `cliff_on_frames` ↑ (3 → 5) |
| 해제가 너무 느림 | `cliff_off_frames` ↓ (10 → 6) |

바닥이 270~336mm이므로 800mm는 **2.4~3.0배 여유**다. 실측 변동폭이 10~11mm라
어지간해서는 오탐이 안 난다. 먼저 화면에서 R6·R7 실측값을 보고 조정할 것.

### 4단계 — 모터 연동 검증 (⚠ 바퀴 띄우고)

**로봇을 받침대에 올려 바퀴가 공중에 뜬 상태**에서 시작한다.

라파1:
```bash
export TURTLEBOT3_MODEL=waffle
ros2 launch turtlebot3_bringup robot.launch.py
```

라파2 (터미널 3개):
```bash
python3 tof.py
python3 mqtt.py
ros2 topic hz /cmd_vel
```

**통과 기준**

- `ros2 topic hz /cmd_vel` → 약 20Hz

## 6.6 미해결 — 가구 밑 빈공간을 낭떠러지로 오탐 (최우선)

**실주행에서 발견.** 의자 다리 옆에서 로봇이 전진하지 못했다. 사용자 관찰:
*"의자 다리랑 장애물이 붙어있어서 의자 다리 밑의 빈공간 때문에 로봇이 이동을 못했다."*

**기록이 뒷받침한다** — 낭떠러지 감지 128샘플 중:

| 조건 | 건수 | 해석 |
|---|---|---|
| 전방 < 0.8m 인데 낭떠러지 | **84건** | 앞에 물체가 있는데 바닥이 없다 = 오탐 의심 |
| 전방 ≥ 0.8m 이고 낭떠러지 | 44건 | 앞이 뚫림 = 진짜 낭떠러지 가능 |

실제 샘플: `F 0.31m` 인데 `cliff[..C]`, `F 0.34m` 인데 `cliff[CCC]`.
**앞 31cm 에 의자가 있는데 낭떠러지가 뜬다.**

**추정 원인**: 의자 다리가 그 뒤 바닥으로 가는 빔을 가려 **그림자(occlusion)** 를
만들고, 그 셀들이 무응답이 되면서 "바닥 없음 → 낭떠러지" 로 판정된다.
로그의 `1118mm > 임계 800mm` 도 빔이 바닥을 못 맞고 멀리 간 흔적이다.
**다만 셀 단위 패턴을 확인하지 못했다** — 어느 열이 죽는지 봐야 확실하다.

**왜 치명적인가**: 휠체어의 주 사용 환경이 **책상·의자·침대가 있는 실내**다.
가구 앞에서 전진이 막히면 기능을 못 쓴다. 조향 채터링(§6.5)은 승차감 문제지만
이건 동작 불능이다. **우선순위가 훨씬 높다.**

**고칠 방향 (미구현, 검증 필요)**

같은 방향에 **가까운 장애물이 있으면 낭떠러지 판정을 억제**한다.

- 안전성 논거: 앞에 물체가 가까우면 장애물 회피가 이미 로봇을 세운다
  (`front_stop_distance` 0.20m 에서 완전 정지). 그 위에 낭떠러지 차단을 더하는 건
  안전을 보태는 게 아니라 **탈출을 막는 것**이다.
- 남는 위험: **낮은 턱 너머가 진짜 낭떠러지**인 경우(하역장 가장자리 등).
  억제 조건을 "장애물이 낭떠러지 ROI 보다 **가까울 때만**" 으로 제한하면 대부분 걸러진다.

**다음에 할 일 (순서)**

1. 낭떠러지 트리거 시 **8x8 원본을 통째로 덤프**하는 진단 추가
2. 의자 상황 재현 → 어느 셀이 죽는지 확인 (추측으로 안전 로직을 손대지 않는다)
3. 확인된 패턴에 맞춰 억제 로직 구현 → 실주행 검증

## 8. VFH 알고리즘 전환 가이드

### 8.1 먼저 — 현재 알고리즘의 정체

현재 구현은 VFH가 **아니다**. 정식 분류하면:

> **임계값 기반 반응형 회피** (threshold-based reactive avoidance)
> = 유한 상태 머신(FSM) + 히스테리시스(Schmitt trigger) + 비례 제어(P-control)

공유제어 문헌에서는 **safeguarded teleoperation**(보호된 원격조종)이라 부른다.
"이름 붙은 알고리즘"이라기보다 직접 설계한 휴리스틱 규칙 집합이다.

### 8.2 핵심 문제 — 데이터의 98%를 버리고 있다

```
현재:  8×8 = 64셀  ──min()──►  숫자 1개
       센서 3개 × 64셀 = 192셀  →  숫자 3개
```

VL53L8CX는 FoV 45°에 8열이므로 **열 하나당 약 5.6°**다. 센서 3개면
**약 135°를 24개 각도 구간**으로 볼 수 있는데, `min()`이 이걸 전부 뭉갠다.

그 결과 다음 두 경우가 완전히 같은 값으로 보인다:

```
  A: 얇은 기둥 하나          B: 벽이 시야 전체를 막음
  ┌────────────────┐        ┌────────────────┐
  │      ██        │        │████████████████│
  └────────────────┘        └────────────────┘
      min = 0.4m                min = 0.4m
   → 옆으로 통과 가능          → 절대 통과 불가
```

`min()`은 **감지에는 안전하지만 조향에는 정보가 없다.**

### 8.3 VFH 계열 정리

| 버전 | 발표 | 추가된 것 |
|---|---|---|
| VFH | Borenstein & Koren, 1991 | 극좌표 히스토그램 + valley 선택 |
| VFH+ | Ulrich & Borenstein, 1998 | 로봇 폭 팽창, 원호 궤적 검증, 비용함수 |
| VFH* | 2000 | A* 기반 앞날 예측 (지역 최소점 완화) |

> 휠체어 적용 전례가 있다: 미시간대 **NavChair** 스마트 휠체어가 VFH를 변형한
> **MVFH(Minimum VFH)** 를 사용했고, VFH 원저자 Borenstein이 참여했다.
> 반면 임계값 FSM 방식은 그런 전례가 없다.

### 8.4 이 하드웨어에서의 구현 방법

#### 단계 0 — 센서 → 각도 매핑

```
센서 배치: front 0°, left +45°, right −45°   (ROS 관례: +z = 좌회전 CCW)
각 센서 FoV 45° → 8열 → 열당 5.625°

right 센서: −67.5° ~ −22.5°   (열 C0..C7)
front 센서: −22.5° ~ +22.5°
left  센서: +22.5° ~ +67.5°
────────────────────────────────
전체 커버리지: −67.5° ~ +67.5° = 135°, 24개 섹터
```

섹터 k(0~23)의 중심각:
```python
theta_k = -67.5 + 5.625 * (k + 0.5)   # degree
```

#### 단계 1 — 극좌표 히스토그램

각 섹터의 대표 거리는 **장애물 ROI(R2~R4) 3개 셀의 최소값**을 쓴다
(세로 3칸이 같은 각도를 보므로).

```python
d_k = min(grid[r][c] for r in obstacle_rows)   # 섹터 k = 특정 센서의 열 c
```

거리를 "장애물 확신도"로 변환 (가까울수록 큼):

```python
m_k = a - b * d_k          # a, b 는 d_max 에서 m=0 이 되도록
                           # 예: d_max=2.0m → a=2.0, b=1.0
m_k = max(0.0, m_k)
```

#### 단계 2 — 로봇 폭 팽창 (VFH+ 핵심)

TurtleBot3 Waffle 폭 281mm → 반경 약 **140mm**. 안전여유 100mm →
유효반경 `r_eff = 240mm`.

거리 d에 있는 장애물은 좌우로 **γ만큼 각도를 더 막는다**:

```python
gamma = asin(r_eff / d)    # d > r_eff 일 때만 정의됨
```

| 거리 d | 팽창각 γ | 막히는 섹터 수 (5.625°/섹터) |
|---|---|---|
| 0.3 m | 53.1° | 약 19개 |
| 0.5 m | 28.7° | 약 10개 |
| 1.0 m | 13.9° | 약 5개 |
| 2.0 m | 6.9° | 약 2개 |

> `d <= r_eff(0.24m)` 이면 γ가 정의되지 않는다 = **전 방향 차단**으로 처리한다.
> 이게 현재의 `front_stop_distance`(0.20m)에 대응하는 자연스러운 일반화다.

팽창 적용 후 이진 히스토그램:

```python
blocked[k] = any(m_j > threshold and |theta_k - theta_j| < gamma_j
                 for j in sectors)
```

#### 단계 3 — Valley 탐색

`blocked`가 False인 **연속 구간**이 valley다. 폭이 `s_max`(예: 4섹터 ≈ 22.5°)
이상이면 wide valley, 미만이면 narrow valley.

```python
valleys = [(start, end) for 연속된 free 구간]
```

Valley가 하나도 없으면 → **정지** (현재 FSM의 "양쪽+정면 막힘 → STOP"에 대응).

#### 단계 4 — 목표 방향 선택

**핵심**: 목표 방향 = **사용자 조이스틱이 가리키는 각도**.
이렇게 하면 공유제어 의도가 그대로 유지된다.

```python
theta_target = atan2(joy_angular_z, joy_linear_x)   # 조이스틱 방향
```

VFH+ 비용함수로 후보 각도를 평가한다:

```python
g(c) = mu1 * delta(c, theta_target)      # 사용자 의도에서 벗어난 정도
     + mu2 * delta(c, theta_current)     # 현재 진행방향에서 꺾는 정도
     + mu3 * delta(c, theta_prev)        # 직전 선택에서 바뀐 정도

# mu1 > mu2 + mu3 이어야 목표 지향적으로 동작한다 (VFH+ 논문 조건)
# 공유제어에서는 mu1 을 더 크게 → 사용자 의도 우선
# 예: mu1=5, mu2=2, mu3=2
```

`mu3`가 **떨림 방지** 역할을 한다. 현재 구현의 히스테리시스에 대응한다.

#### 단계 5 — 속도 결정

```python
# 선택 각도 방향의 장애물 근접도에 비례해 감속 (현재 비례 조향과 동일 사상)
v = min(joy_linear_x, v_max) * (1 - m_selected / m_max)
w = k_p * (theta_selected - 0)      # 선택 각도로 조향
```

### 8.6 권장 구조 — 계층 분리

VFH로 **전부** 바꾸지 말고, 안전 규칙은 FSM으로 남길 것을 권한다.

```
┌─ 바깥 안전 계층 (기존 FSM 유지) ─────────────┐
│  · 낭떠러지 차단   ← 최우선, 절대 우회 불가    │
│  · 데드맨 (손 떼면 정지)                      │
│  · 센서 무효 = 막힘                          │
│  · 최종 속도 클램프                          │
│         ↓ 이 안에서만 조향 자유              │
│  ┌─ 안쪽 조향 계층 (VFH+ 로 교체) ────────┐  │
│  │  8×8 열 → 24섹터 히스토그램            │  │
│  │  → 폭 팽창 → valley → 비용함수 → 각도  │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
```

이유: 안전 규칙은 **검증 가능해야** 한다. VFH 내부에 섞으면 "왜 안 멈췄는지"
추적이 어려워진다. 지금의 25건 로직 검증도 이 구조라서 가능했다.

### 8.7 장단점 비교

| 항목 | 현재 (임계값 FSM) | VFH+ |
|---|---|---|
| 로봇 폭 고려 | ❌ 없음 | ✅ 장애물 팽창으로 명시적 반영 |
| 통과 가능 판단 | ❌ 못함 | ✅ 폭 이상인 valley만 선택 |
| 좁은 문 통과 | 좌/우 이진 선택뿐 | ✅ 최적 각도 계산 |
| 궤적(선회반경) 검증 | ❌ 없음 | ✅ 원호 기반 차단 |
| 다중 장애물 | ❌ 구분 불가 | ✅ 사이 틈 탐색 |
| 센서 노이즈 내성 | 약함 (단일 프레임) | ✅ 히스토그램 누적 |
| 지역 최소점 탈출 | ❌ 진동 가능 | 부분적 (VFH*는 개선) |
| **예측 가능성·검증** | ✅ **매우 높음** | 파라미터 많아 어려움 |
| **연산량** | ✅ **매우 낮음** | 약간 높음 (실시간 충분) |
| **반응 지연** | ✅ **즉각** | 누적 때문에 수 프레임 |
| 파라미터 수 | 12개 | 20개+ |
| 튜닝 난이도 | 낮음 | 높음 |
| 코드 복잡도 | 낮음 (읽기 쉬움) | 중간 |

### 8.8 전환 판단 기준

**VFH로 바꿔야 하는 경우:**
- 좁은 문·복도를 자주 통과해야 함
- 로봇 폭이 커짐 (휠체어 60~70cm)
- 여러 장애물 사이를 지나가야 함
- 현재 방식에서 "지나갈 수 있는데 멈춘다"가 자주 발생

**현재 방식을 유지해도 되는 경우:**
- 넓은 실내에서 단순 충돌 방지가 목적
- 검증·설명 가능성이 중요 (연구 발표, 안전 인증)
- 파라미터 튜닝 시간이 부족
- **TurtleBot3 시연이 최종 목표**

### 8.9 전환 시 권장 순서

```
1. 현재 코드를 브랜치로 보존           ← 되돌아갈 곳 확보
2. 섹터 매핑만 먼저 구현 → 웹 화면으로 24섹터 시각화
   (히스토그램이 실제 장애물과 맞는지 눈으로 확인)
3. 히스토그램 + 팽창 구현 → 로그로 valley 확인 (아직 제어 안 함)
4. 비용함수 + 조향 구현 → 바퀴 띄우고 출력값만 관찰
5. 안전 계층(낭떠러지·데드맨)은 손대지 않았는지 재확인
6. 로직 검증 25건 다시 통과시키기       ← 회귀 방지
7. 저속 실주행
```

**2~3단계에서 눈으로 확인하는 게 중요하다.** 섹터 매핑이 틀리면
(예: left/right 부호 반대) VFH가 장애물 쪽으로 조향한다.

## 9. 휠체어 적용 시 고려사항

현재 설계는 **연구·시연용이며 사람을 태우기엔 부족하다.** 알고리즘 선택보다
아래가 먼저다.

| 문제 | 현재 상태 | 필요한 것 |
|---|---|---|
| 후방 미감지 | 센서 3개 모두 전방 | 후방 ToF (후진 사고가 주요 원인) |
| 발판·발 미감지 | 무릎 높이만 봄 | 낮은 높이 센서 |
| 상부 장애물 미감지 | 테이블 모서리 못 봄 | 상부 센서 |
| 센서 단일화 | 하나 고장 = 그 방향 실명 | 이중화 |
| 소프트웨어 정지만 존재 | 프로세스 죽으면 워치독 의존 | 하드웨어 비상정지 |
| 급정지 제한 없음 | 즉시 0 가능 | 감속도 제한 (전복·이탈 방지) |
| 속도 대비 감지거리 | 0.5m 고정 | 속도 비례 (1~2m/s면 이미 늦음) |
| 폭 인식 없음 | 28cm 로봇 기준 | 60~70cm 반영 (= VFH+ 필요 이유) |

**파라미터만 키워서는 안 된다.** `side_min_distance`를 0.15 → 0.35로 바꾼다고
휠체어가 안전해지지 않는다. "내가 저기 들어갈 수 있는가"라는 개념 자체가
현재 로직에 없기 때문이다. 이것이 VFH+ 전환이 필요한 구조적 이유다.

## 부록 C — MQTT JSON 스키마 (`robot/cmd`)

```json
{
  "seq": 12345,
  "stamp": 1785918145.866,
  "linear_x": 0.0,
  "angular_z": 0.4,
  "mode": "CLIFF_BLOCK",
  "cliff_detected": true,
  "obstacle_detected": false,
  "tof":    { "front": 0.83, "left": 0.21, "right": null },
  "sensor": { "front": "ok", "left": "ok", "right": "empty" },
  "cliff":  { "front": true, "left": false, "right": false },
  "joy":    { "engaged": true, "linear_x": 0.15, "angular_z": 0.4 }
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `seq` | int | 순번. 유실·순서역전 감지용 |
| `stamp` | float | tof.py 기준 UNIX 시각. 지연 측정용 |
| `linear_x` / `angular_z` | float | 최종 속도 (m/s, rad/s) |
| `mode` | string | `NORMAL` / `STOP` / `CLIFF_BLOCK` / `AVOID_LEFT` / `AVOID_RIGHT` |
| `cliff_detected` | bool | 낭떠러지 통합 플래그 |
| `obstacle_detected` | bool | 장애물 통합 플래그 |
| `tof` | object | 방향별 거리 (m). **측정 없으면 `null`** |
| `sensor` | object | `ok`(측정됨) / `empty`(정상이나 물체 없음) / `offline`(프레임 없음) |
| `cliff` | object | 방향별 낭떠러지 — 디버깅용 |
| `joy` | object | 조이스틱 원본 — 회피 개입량 확인용 |

> JSON 키에 점(`.`)을 못 써서 `linear.x` → **`linear_x`**, `angular.z` → **`angular_z`**.
> `seq`/`stamp`는 요구사항에 없었지만 유실·지연 진단에 필수라 추가했다.

> **`tof`가 `null`인 이유**: `treat_stale_as_blocked`는 센서 무효를 제어상 `0.0m`(막힘)으로
> 치환한다. 그 대체값을 실제 측정처럼 보고하면 화면에 `0.00m`로 떠서 진짜 근접과 구분되지
> 않는다. 그래서 **제어에는 대체값을, 보고에는 `null`**을 쓴다 (§5 오류 1번).
